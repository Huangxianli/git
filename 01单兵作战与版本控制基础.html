🏛️ Git 的核心架构：三大区域（Three Trees）

Git 区别于传统集中式版本控制（如 SVN）的最大特点，在于它在工作目录和版本历史之间设计了一个至关重要的缓冲地带——暂存区（Index）。

Tree 1 · 实体层
工作区 (Working Dir)
你的项目文件夹
你在 IDE 中能直接看到和修改的代码文件。任何增删改在此处于“未跟踪/未暂存”状态，不受版本保护。
Tree 2 · 缓冲层
暂存区 (Index / Stage)
.git/index
即将提交的快照清单。在此精细挑选改动，实现高内聚的原子提交（Atomic Commit），解决合并冲突。
Tree 3 · 持久层
版本库 (Repository)
.git/objects/
不可变的永久对象数据库。HEAD 指针指向当前正在检出的分支与 commit 节点，提供完整的时光机倒流能力。

🔍 拆解 .git/objects：Git 的三类核心数据对象

Blob 对象 只存文件内容
存储文件的 zlib 压缩后纯文本内容。Blob 对象不存文件名、不存路径、不存权限。若 10 个不同名字的文件内容相同，在 Git 库中仅占用一个 Blob 存储！
Tree 对象 目录与文件名结构
相当于文件系统的“文件夹”。记录了该目录下包含的所有文件名、文件执行权限以及对应的 Blob 或子 Tree 对象的 SHA-1 哈希映射。
Commit 对象 历史快照元数据
顶层快照容器。包含：指向项目根目录 Tree 的指针（完整快照）、父 Commit 节点哈希、作者与提交者签名信息、以及 Commit Message。
🔄 文件 4 大生命周期状态与流动链条

Git 视角下，一个文件必然处于以下状态之一：

1. 未跟踪 (Untracked)
新建但未执行 git add 的文件，Git 完全不过问其内容。
2. 已修改 (Modified)
文件受版本控制，你在工作区改了代码，但还未加入暂存区。
3. 已暂存 (Staged)
执行了 git add，文件被打包进即将 commit 的快照中。
4. 未修改 (Unmodified)
执行了 git commit 后，工作区与仓库历史完全一致。
⚡ 阶段一高频命令速查手册

1. 配置全局作者与初始化

# 设定签名（必须是有效格式，决定 GitHub 提交绿墙归属）
git config --global user.name "你的名字"
git config --global user.email "you@example.com"

# 设置默认分支名为主流标准的 main（替代老旧 master）
git config --global init.defaultBranch main

# 本地文件夹初始化版本库（生成 .git）
git init

2. 状态查看与暂存

# 精简状态输出（XY 双列标识：X 为暂存区状态，Y 为工作区状态）
git status -s

# 暂存当前路径下的所有新增、修改与删除
git add .

# 极客技巧：交互式挑选代码片段（Hunk）暂存
git add -p [文件名]

3. 提交与后悔药追加

# 规范提交
git commit -m "feat(auth): 新增手机短信验证码登录接口"

# 漏加文件或写错信息？吸纳暂存区并重写上一次 commit（不产生新节点）
git commit --amend --no-edit

4. 差异比对 (Diff) 三剑客

# 比对：工作区 vs 暂存区（检查还有哪些代码没执行 git add）
git diff

# 比对：暂存区 vs 上一次 Commit（检查即将 commit 的代码长什么样）
git diff --staged

# 比对：工作区 vs 上一次 Commit（全景比对自上次 commit 以来的所有改动）
git diff HEAD

5. 现代撤销操作 (Restore)

# 丢弃工作区中文件的未暂存改动（恢复原状）
git restore [文件名]

# 将已暂存的文件移出暂存区，退回工作区（保留文件内容）
git restore --staged [文件名]

# 从版本控制中移除追踪，但物理硬盘保留该文件
git rm --cached [文件名]

🎯 真实工程场景大考

请先独立思考你在面对该场景时会如何敲击命令，再点击“查看标准题解与原理解析”核对答案！

SCENARIO 01 高频实战 · 撤销篇
代码写乱了，如何精准放弃单个文件的本地修改，而不误伤其他文件？
情境设定：你修改了 app.js、style.css 和 config.json。检查时发现 app.js 和 style.css 逻辑很棒，但 config.json 改得一团糟且严重报错。你想彻底放弃 config.json 的改动，恢复成上次提交时的样子，但绝不能影响其他两个文件。此时你还没敲过任何 git add。

✅ 标准命令

git restore config.json
原理解析：git restore <file> 是 Git 2.23 推出的现代化专用撤销命令（旧版本对应 git checkout -- config.json）。它会从暂存区（若暂存区为空，则直接从当前 HEAD commit）抓取该文件的快照覆盖工作区物理文件。由于指定了具体文件名，其他修改的文件丝毫不受影响。
SCENARIO 02 团队安全 · 误操作防范
误敲 git add . 把密钥文件暂存了，如何在不删本地文件的前提下安全移出？
情境设定：你在本地写了个 .env.local，里面包含了阿里云和数据库密码。敲键盘顺手一抖输入了 git add .。执行 git status 发现该文件变成了绿色（已处于暂存区）。此时千万不能直接 commit！你该如何把它移出暂存区，且保证本地硬盘上的密码文件不被删除？

✅ 标准命令步骤

# 步骤 1：移出暂存区（保留本地文件内容）
git restore --staged .env.local

# 步骤 2：写入忽略规则，彻底杜绝后续再次被 add 误录
echo ".env.local" >> .gitignore
原理解析：git restore --staged <file>（或经典命令 git rm --cached <file>）会将指定路径从暂存区快照树中注销，但不会碰触物理工作区磁盘。千万不能手滑执行 git rm -f，否则本地实体文件将被直接物理删除！
SCENARIO 03 洁癖提交 · 历史美化
刚执行完 commit 发现漏加了一个小图标，如何不产生垃圾多余提交进行修补？
情境设定：你刚刚完成了登录界面并执行了规范提交：git commit -m "feat(auth): 完成用户登录页面布局"。刚敲完回车，你突然意识到刚才在 assets/icon-user.svg 里的图标漏提交了！如果再单独提交一次写着 "fix: 漏了图标" 的 commit，提交树会非常碎且难看。怎么做最优雅？

✅ 标准命令步骤

# 1. 把漏掉的图标加入暂存区
git add assets/icon-user.svg

# 2. 追加合并到上一次提交，保持原提交信息不变
git commit --amend --no-edit
原理解析：git commit --amend 会将当前暂存区中的变更与上一次 Commit 合并，创建并替换为一个全新的 Commit 对象。--no-edit 避免重复弹窗编辑信息。只要该 commit 还没推送到公共远端，用此方法能保持提交树极度清爽专业。
SCENARIO 04 高级进阶 · 交互式挑选
同一个文件改了 10 处，只想暂存提交其中修复 Bug 的 3 处，怎么做到？
情境设定：你在 utils.js 里面写了一天：前面 20 行修复了一个“时区计算错误”的紧急 Bug；中间和末尾又写了 80 行新的“大数格式化”功能（还在实验中）。现在生产线要立即发版修复时区 Bug，但未完成的大数功能绝不能提交。如何只暂存该文件内的部分改动？

✅ 标准命令：交互式补丁暂存 (Patch Mode)

git add -p utils.js
交互按键诀窍：终端会把代码切成一个个片段（Hunk）询问 Stage this hunk [y,n,q,a,d,s,e,?]?：
  • 按 y：暂存这块代码（针对时区 Bug 修复的代码块）；
  • 按 n：不暂存这块代码（针对大数功能的代码块）；
  • 按 s：如果一段代码块混杂，输入 s 可以把块进一步拆细！
挑选完毕后，执行 git commit -m "fix(utils): 修复时区计算偏差"，即可完成完美的原子提交！
SCENARIO 05 架构思考 · 面试必考
为什么 Git 必须设计“暂存区”？像 SVN 那样直接 commit 不更简单吗？
情境设定：很多从 SVN 转过来的程序员常抱怨：“为什么每次提交非得先 add 再 commit？这不是多此一举吗？”请从软件工程和 Git 底层架构角度给出强有力的回答。
三大核心论点：
  1. 原子性提交（Atomic Commits）解耦：工作区经常同时产生多个不同目的的改动。暂存区让开发者拥有从容筛选变动、拆分逻辑独立提交的能力，而不是被迫一锅端。
  2. 三方合并与冲突处理的仲裁所：当发生合并冲突时，冲突解决状态正是通过 git add 登记到 index（暂存区包含 Stage 1/2/3 多个分支祖先版本），是保障合并安全的核心机制。
  3. 最后一次预演与 Code Review 关卡：在代码正式固化进历史快照前，利用 git diff --staged 进行最后一次审阅，防止手滑提交测试日志或密码。
SCENARIO 06 硬核极客 · 底层探测
不借助任何工具，如何证明 .git/objects 中存的究竟是什么？
情境设定：你刚执行了一次 git commit。主管说：“你说 Git 是个基于内容哈希的数据库，你怎么在命令行里证明这一点？”请使用 Git 底层管道命令（Plumbing command）一窥究竟。

✅ 底层探测命令

# 1. 打印当前最新 Commit 对象的原始明文
git cat-file -p HEAD

# 2. 从上面的输出拿到 Tree 哈希，打印该 Tree 对象的目录内容
git cat-file -p [tree-hash]

# 3. 从 Tree 输出里拿到某个文件的 Blob 哈希，打印文件原始内容
git cat-file -p [blob-hash]
验证成果：你会亲眼目睹 Commit 包含指向 Tree 的哈希；Tree 里包含文件名与其对应的 Blob 哈希；而 Blob 里面只有干净的文件压缩内容！这就是 Git 优美而高效的底层世界。
